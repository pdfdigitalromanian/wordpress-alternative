# Local setup

Adapted for an environment with **no Docker** (confirmed permanent) — see
"Local database strategy" in `docs/architecture.md` for why this differs
from a typical Supabase/Medusa quickstart.

## Prerequisites (already satisfied on this machine)

- Node.js (this machine runs v24; Medusa's `engines` field wants
  `^20.19.0 || >=22.12.0` — v24 has worked for install/migrate/dev so far
  in this session, but is unverified upstream. If anything in `apps/medusa`
  misbehaves in a way that looks version-related, that's the first thing
  to suspect.)
- pnpm (`corepack`/`pnpm@11.21.0`, pinned in root `package.json`)
- Homebrew `postgresql@16` — already running as a `brew services` daemon
- Homebrew `redis` — already running as a `brew services` daemon
- Supabase CLI (`brew install supabase/tap/supabase`) — installed

## One-time setup already done in this session

```bash
# Medusa's dedicated local Postgres role + database (NOT the CMS database)
psql -U "$(whoami)" -d postgres -c "CREATE ROLE medusa WITH LOGIN PASSWORD 'medusa_local_dev_only';"
psql -U "$(whoami)" -d postgres -c "ALTER ROLE medusa CREATEDB;"
psql -U "$(whoami)" -d postgres -c "CREATE DATABASE medusa OWNER medusa;"

# apps/medusa
cd apps/medusa
npx medusa db:migrate   # ran the initial Medusa v2 module migrations + demo seed
npx medusa user -e <your-email> -p <a-local-only-password>   # local admin user
```

Verify any time with:

```bash
./scripts/check-local-services.sh
```

## Running things

```bash
# from repo root
pnpm install

# CMS web app (React Router SSR, Vite)
pnpm --filter @digital-romanian/web dev        # http://localhost:5173

# Medusa backend (health at /health, native Admin at /app)
pnpm --filter @digital-romanian/medusa dev     # http://localhost:9000
```

Both were verified booting and serving real responses during the M0
session (SSR HTML from `/`, `200` from Medusa `/health` and `/app`, `400`
— not a crash — from `/store/products` without a publishable key).

## CMS database (Supabase) — manual step required from you

Supabase's full local stack (`supabase start`) needs Docker, which this
environment doesn't have. Per your decision on 2026-09-19, the CMS
develops directly against the hosted project instead of a local one:

```bash
supabase login          # interactive browser OAuth — only you can do this
supabase link --project-ref nsfcmwlbippjjlpvjoyd
```

Done as of 2026-09-20: linked, and the M1 schema (`workspaces`,
`workspace_memberships`, `sites`, `site_domains`, RLS policies) is pushed
and live on the hosted project. Migrations in `supabase/migrations/` are
pushed with:

```bash
supabase db push
```

Because there's no local CMS database to test against first, every
migration gets written carefully and reviewed before `db push`, and
destructive operations (`supabase db reset` against the linked project,
dropping columns/tables) are called out explicitly before running.

Cross-workspace RLS isolation is covered by a real integration test run
against the hosted project (creates two throwaway users, exercises the
policies, deletes everything it made):

```bash
pnpm test:rls
```

`apps/web/.env.local` (gitignored) holds the hosted project's URL,
publishable key, and a secret key (currently the legacy `service_role`
JWT — see the comment in that file about rotating to the new
`sb_secret_...` format) — this is what `pnpm test:rls` reads via
`--env-file`.

## Medusa environment variables

`apps/medusa/.env` holds real local secrets (gitignored). Regenerate with:

```bash
openssl rand -hex 32   # JWT_SECRET, COOKIE_SECRET, AUTH_MFA_ENCRYPTION_KEY
```

`apps/medusa/.env.template` is the checked-in placeholder reference.

## Web app environment variables

`apps/web/.env.example` documents the contract (public `VITE_` vars vs.
server-only vars vs. the optional local Medusa bootstrap connection). No
`apps/web/.env.local` exists yet — it's needed once Supabase auth wiring
starts in M1.

## Known gaps from this session

- Node v24 vs. Medusa's documented `^20.19.0 || >=22.12.0` range — works
  so far, not guaranteed for every Medusa package going forward.
- `apps/medusa`'s local Postgres migration also ran a bundled demo-data
  seed script (`src/migration-scripts/initial-data-seed.ts`, generated by
  `create-medusa-app`) — it created a demo region, sales channel, stock
  location, and one demo product in the **local** database only. This is
  scaffolding noise, not real store content; clear it out before this
  becomes a real store, and don't let it leak into any shared/staging
  database via a `db:migrate` run there.
- No production deployment target chosen yet for `apps/medusa` (persistent
  Node host — Railway/Render/Fly/Medusa Cloud/etc. — undecided). See
  `infra/README.md`.
